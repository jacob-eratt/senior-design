The new design is standalone; it does not instantiate the old `mac_int8`,

cannot drive this new preload interface.

## Compute architecture

The engine computes full Conv0: input 32 x 32 x 3, 26 output channels,
3 x 3 kernel, stride 1, SAME zero padding. Its output is 32 x 32 x 26 signed
INT32 convolution-plus-bias values, with BatchNorm already folded into parameters.

It divides the 1,024 output positions into 64 tiles of 16 adjacent pixels:
the left half of row 0, right half of row 0, left half of row 1, and so on.
Each spatial position has 26 MAC lanes, giving **16 x 26 = 416 lanes**.

```text
16 replicated input memories -> 16 input samples per compute cycle
                                     |
26 weight banks -> 26 weights ------> 16 groups of 26 MACs
                     broadcast       |
                                416 INT32 accumulators
                                     |
                              4 results per output beat
```

The 26 weights for a kernel tap are shared across all 16 spatial groups.
Each group's one input sample is broadcast to its 26 channel MACs. Over 27
successive tap issues, each accumulator receives all products for one output.
The registered pipeline is memory read -> product -> accumulation.

The controller loads biases, issues 27 consecutive tap reads, drains the last
two pipeline stages, and emits the tile's 416 results. It then reuses the same
416 lanes for the next tile. It does not compute and drain different tiles
concurrently; double buffering is a possible later performance improvement.

Each multiplier requests DSP mapping with `use_dsp="yes"`. There are 416
explicit signed 8 x 8 products, 416 registered 16-bit products, and 416 INT32
accumulators. Actual DSP mapping, accumulator placement, resource totals, and
clock frequency must be established by synthesis and implementation.

## Local storage and preload

Rather than exposing a 16-read-port RAM, the design stores 16 identical copies
of the image. Each copy serves one spatial group. Every accepted image write
updates all copies. Their total payload is 49,152 bytes (48 KiB); block-RAM
allocation may be larger due to primitive capacity and configuration. The RTL
requests block RAM for these copies and uses synchronous reads.

Weights are split into 26 banks of 27 bytes: 702 bytes total. They request
distributed RAM and have registered reads. Bias storage is 26 INT32 words,
104 bytes. The module contains no complete output-image memory.

| Port group | Contents and addressing |
|---|---|
| `image_we`, `image_addr[11:0]`, `image_data[7:0]` | Signed input bytes, HWC address `(y*32+x)*3+c`, range 0..3071 |
| `weight_we`, `weight_addr[9:0]`, `weight_data[7:0]` | Signed weight bytes, OHWI address `oc*27+ky*9+kx*3+ic`, range 0..701 |
| `bias_we`, `bias_addr[4:0]`, `bias_data[31:0]` | Signed bias word for output channel 0..25 |

Writes are accepted on rising edges when `load_ready && *_we`. The independent
ports may write simultaneously. Invalid addresses are ignored. Fully initialize
all memories before first use; the hardware does not track whether loading is
complete. No external read interface is used during calculation.

`rst` is synchronous, active high. It aborts computation and clears pipeline
valids and accumulators; it **does not erase loaded memories**. Reset blocks
writes. `start` while idle has priority over writes, so `load_ready` is low on
a start cycle. Start and writes while busy are ignored. Pulse start for one
cycle; holding it high can launch another frame once the engine returns idle.

For successive images, weights and biases can stay resident. Replace only the
image while idle, then start again. Loading the next image during computation
is not supported by this single-buffer design.

## Output protocol

The default `OUTPUT_LANES=4` emits a 128-bit beat containing four signed INT32
values. These are packed in ascending HWC address order:

```text
out_data[ 31: 0] = result at out_addr + 0
out_data[ 63:32] = result at out_addr + 1
out_data[ 95:64] = result at out_addr + 2
out_data[127:96] = result at out_addr + 3
```

`out_addr` is a **32-bit-word index**, not a byte address. Multiply by four to
obtain an output byte offset. The address sequence is 0, 4, 8, ... 26620.
A beat can cross a channel/pixel boundary; always use its address rather than
assuming each beat belongs to one pixel.

Accept a beat on `out_valid && out_ready` at the rising edge. While stalled,
valid, data, and address remain stable. `done` pulses after the final accepted
beat, when `busy` clears. Outputs are meaningful only while `out_valid` is high.

`OUTPUT_LANES` can be a positive divisor of 416, such as 1, 2, 4, 8, 16, or 26.
Every beat is full. Changing this parameter changes output width and drain
time, not the 416 MAC lanes. Set the testbench's matching parameter too; it
passes the value to the DUT. Unsupported parameter values are not a valid
hardware configuration.

This wide bus is intended for internal FPGA buffers or a future bus adapter.
It is not a board pin assignment. A board top still needs memory/host control,
clock and pin constraints, and a practical external interface.

## Performance accounting

The layer requires 718,848 products. The engine issues 416 products per active
compute cycle, giving 1,728 tap-issue cycles across the 64 tiles. This alone is
not total latency.

For `OUTPUT_LANES=4`, each tile also needs 104 output cycles, one bias-init
cycle, and two pipeline-drain cycles. From an accepted start through the final
accepted output, the intended no-stall schedule is:

```text
1 + 64 * (1 + 27 + 2 + 104) = 8,577 rising edges, counting the start edge
```

This is a schedule calculation, not a measured simulation result. Preload is
additional: 3,072 image writes, with the 702 weight and 26 bias writes able to
overlap on their independent ports. Output stalls add cycles. At a hypothetical
100 MHz, 8,577 cycles corresponds to about 85.8 microseconds; achievable clock
frequency is unverified. The testbench deliberately stalls the final beat and
some other beats, so its reported counts will be higher.

The current serial core's measured synthetic results do not validate this
parallel implementation. DSP count alone also does not establish speed or fit.

## Run in Vivado

Manual setup:

1. Add `conv0_416_dsp.v` as a **Design Source**.
2. Add `tb_conv0_416_dsp.sv` as a **Simulation Source**, type **SystemVerilog**.
3. Set simulation top to **tb_conv0_416_dsp**.
4. Run behavioral simulation, then **run all**. A default 1,000 ns run is too short.

For automatic setup including the existing Python golden fixture, close any
previous simulation and enter in the Vivado project Tcl console:

```tcl
source {C:/Users/Ibrah/Desktop/ECE_364D/senior-design/resnet8_project/rtl/setup_xsim_416.tcl}
launch_simulation -simset sim_1 -mode behavioral
```

On a fresh clone, the setup falls back to the checked-in `fixtures/` directory
when full generated artifacts are absent; Python installation is not required
to run that bundled accumulator fixture.

The setup selects `OUTPUT_LANES=4`, replaces old simulation parameter overrides,
enables the Python fixture, and avoids automatic waveform loading. It does not
change the synthesis top. For synthetic-only tests, set
`resnet_416_use_fixture 0` before sourcing; set it to `1` to enable the fixture
again. If adding files manually, set string parameter `ARTIFACT_DIR` to the
absolute `resnet8/artifacts` path, or supply a matching plusarg. Forward-slash
paths are recommended. Do not use the old 1024-pixel or serial setup scripts.

For synthesis, choose **conv0_416_dsp**, not the testbench, as the design top.
Report actual DSP, LUT, register, and RAM usage before claiming the design fits.

## Testbench coverage and expected results

The testbench preloads data, pulses start, and compares each of the 26,624
accepted output values against an independent signed 64-bit scalar convolution.
The oracle does not inspect DUT internals or reuse its spatial tiling logic.

It checks reset/start priority, reset during calculation and stalled output,
retention of memories across reset, ignored writes/start during busy, invalid
write addresses, signed extremes, bias counted once, border padding, spatial
tile boundaries, output lane packing, exact addresses, no missing/duplicate
results, backpressure stability, completion timing, and restart without reloading.
Unknown output bits or missing fixture words cause a fatal error.

Five synthetic frames cover zero input with extreme signed biases, signed INT8
boundary patterns, random input/weights, replay of the random frame without
reloading, and sparse impulses at edges and tile boundaries. The optional
sixth frame uses:

```text
ARTIFACT_DIR/layer_vectors/conv0/input.mem
ARTIFACT_DIR/export/conv0_weights.mem
ARTIFACT_DIR/export/conv0_bias.mem
ARTIFACT_DIR/layer_vectors/conv0/expected_acc.mem
```

The Python accumulator fixture is checked against the scalar oracle first.
Synthetic-only success should report five frames and 133,120 comparisons.
With the fixture, success should end with a line shaped like:

```text
PASS: tb_conv0_416_dsp frames=6 comparisons=159744 cycles=... python_fixture=1
```

The six-frame message is the expected golden-enabled result, not a recorded
pass. The reported five-frame synthetic-only result passed. This core still does not
perform requantization, ReLU, residual operations, pooling, dense classification,
or the later convolution configurations. Those remain the next integration work.
